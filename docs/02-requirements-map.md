## Цели и ценность продукта

### Цель проекта

Разработать первую эксплуатационную версию BAS-платформы и провести ее внутреннюю апробацию на изолированных тестовых стендах и заранее согласованных контролируемых сегментах корпоративной ИТ-инфраструктуры

### Ценность для внутренних пользователей

Платформа должна позволять:

- Проводить контролируемую симуляцию сценариев кибератак

- Проверять способность существующих сердств защиты обнаруживать и блкировать моделируемую активность

- Получать централизованные результаты проведения симуляций

- Повторно запускать утвержденные сценарии

- Безопасно завершать и откатывать результаты симуляций

- Выявлять ограничения текущих защитных мер

### Результат Фазы №1

Результатом является не коммерческий продукт, а первая эксплуатационная версия, внутренняя апробация, подтвержденияе технологической реализуемости и формирование основы для решения о переходе к следующим фазам

- Администратор платформы

- Оператор симуляций

- Аналитик ИБ

- Эксперт по сценариям

- Руководитель ИБ

### Аутентификация

- Обязательная аутентификация пользователей

- Двухфакторная аутентификация

- Разграничение прав доступа в соответствии с ролью

**Уточнить на сборе требований:**

- Интеграция с корпоративным IdP

- Требования к сроку жизни сессии

- Блокировка учетной записи

- Требования к паролям

**Уточнить на сборе требований:**

- Какие именно действия доступны каждой роли

- Может ли оператор самостоятельно создавать/изменять сценарии

- Кто имеет право запускать симуляцию в контролируемом сегменте

## Управление сценариями атак

### Репозиторий сценариев

Платформа должна предоставлять централизированное хранение сценариев

Для сценария должны храниться как миниммум:

- Идентификатор

- Описание

- Класс атаки

- MITRE ATT&CK маппинг

- Версия

- Ожидаемый результат

- Параметры запуска

- Требования к целевой среде

- Правила безопасного завершения

### Классы сценариев Фазы №1

Минимальная граница:

1. Фишинг - не менее 2 сценариев

2. Сетевые атак - не менее 2 сценариев

3. Имитация распространения вредоносного ПО - не менее 2 сценариев

Итого - не менее 6 утвержденных сценариев

### Версионирование

**Необходимо обеспечить контролируемое обновление сценариев:**

- Хранение версии

- Изменение версии

- Предварительное тестирование

- Возможность отката версии

### Безопасность сценария

Перед запуской сценарий должен проходить необходимые проверки и ограничения

**Уточнить на сборе требований:**

- Кто утверждает сценарий

- Какие статусы имеет сценарий

- Какие проверки обязательны перед переводом в доступные для запуска

- Может ли сценарий запускаться повторно

- Кто имеет право изменять утвержденный сценарий

## Управление кампаниями и запуском симуляций

### Создание кампании

**Пользователь должен иметь возможность:**

- Выбрать сценарий

- Выбрать целевые системы/фгенты

- Задать параметры запуска

- Определить время запуска

- Сформировать кампанию

### Запуск

**Поддерживаются:**

- Запуск по расписанию

- Запуск в реальном времени/вручную

### Предварительные проверки

**До запуска должны проверять как минимум:**

- Допустимость цели

- Наличие цели в белом списке

- Отсуствие цели в черном списке

- Лимит параллельных запусков

- Лимит времени выполнения

- Разрешение оператора

- Допустимость конкретного сценария

### Управление выполнением

**Необходимо обеспечить:**

- Отображение статуса кампании

- Остановку выполнения

- Безопасное завершение

- Переход в безопасное состояние при потере связи с критическим компонентом

### Kill Switch

Платформа должна иметь механизм экстренной остановки симуляции

**Для версии Фазы №1 принимается следующая модель:**

- Оператор может экстренно остановить активную кампанию

- Администратор платформы имеет право выполнить глобальную аварийную остановку всех активных кампаний

- После активации kill switch новые действия сценария не запускаются

- Агенты прекращают выполнение активных действий и переходят в безопасное состояние

- Начало остановки должно быть инициировано не позднее 30 секунд с момента подтверждения команды kill switch

- Возобновление симуляций после глобальной аварийной остановки возможно только после завершения проверки инцидента и разрешения уполномоченного сотрудника ИБ

## Безопасность и выполнение отката

### Предварительное тестирование

Каждый сценарий должен быть протестирован на изолированном stage-стенде до допуска к контролируемой внутренней апробации

### Откат и очистка

Для 100% сценариев первой эксплуатационной версии должен существовать и быть протестирован механизм отката

Он должн обеспечивать удаление созданных в ходе симуляции артефактов, включая предусмотренные сценарием:

- Файлы

- Службы

- Ветви реестра

- Учетные записи

- Другие создаваемые артефакты

### Контроль целевой среды

**Необходимо поддержать:**

- Белый список целей

- Чернвй список критических сегментов

- Ограничение параллельных запусков

- Ограничения времени выполнения

- Запрет потенциально разрушительных действий

### Поведение при инциденте

**При возникновении инцидента, связанного с платформой или симуляцией:**

- Новые симуляции блокируются

- Выполняющиеся процессы переводятся в безопасное состояние

- Дальнейшие запуски разрешаются только после асследования и соответствующего разрешения

- Защищенный как от Сервера через Прокси к Агенту

- Взаимная аутентификация

- MFA для пользователей

- Минимальные права агентов

- Аудит действий

- Шифрование репозиториев

- DevSecOps проверки

- Контроль сторонних компонентов

### Производительность

**Зафиксированное требование:**

- CPU агента ≤ 5% в пике при штатном выполнении сценария

**Дополнительно уточнить:**

- RAM

- Допустимую задержку запуска

- Количество одновременно выполняемых кампаний

- Количество агентов

- Количество сценариев

- Объем обрабатываемой телеметрии

### Надежность

**Необходимо определить:**

- Поведение при недоступности Сервера управления

- Поведение при потере агента

- Восстановление после сбоя

- Требования к доступности компонентов

Зафиксировано в уставе: при недоступности Сервера управления или потере связи с агентом новые сценарии не должны запускаться, а активная кампания должна перейти в безопасное состояние

- Windows

- Linux

### Масштабируемость

- Набора сценариев

### Среда

- В заранее согласованных контролируемых сегментах корпоративной инфраструктуры

**Должны быть проведены сценарии трех классов:**

- Фишинг

- Сетевые атаки

- Результаты выполнения сценариев

23. Как организуется взаимная аутентификация? **Апробация**

27. Какие критерии определяют успешность каждого сценария?

Сценарий считается успешно выполненным, если:

a. Выполнены все предусмотренные сценарием действия

b. Действия выполнялись только в разрешенной целевой среде

c. Ожидаемый результат выполнения зафиксирован

d. Результат обнаружения/блокировки СЗИ зафиксирован либо отмечен как «не определен» при недостаточности телеметрии

e. Выполнены предусмотренные сценарием очистка и/или откат

f. Отсутствуют критические нарушения правил безопасного выполнения

28. Кто подписывает результат апробации?

Внутренний Заказчик принимает результаты апробации, Спонсор принимает решение о завершении Фазы №1

29. Как фиксируется обнаружение/блокировка СЗИ?

Обнаружение/блокировка фиксируются на основании событий SIEM/EDR, сопоставленных с ID кампании и временным интервалом выполнения соответствующего действия сценария. При недостаточности телеметрии результат фиксируется как "не определен"

30. Какие условия необходимы для допуска платформы к следующей фазе?

Критерии перехода к Фазе №2 зафиксированы в Уставе проекта и включают технологическую готовность, операционную ценность, повторяемость сценариев и архитектурную готовность к дальнейшему масштабированию

В связи с отсутствием на текущем этапе реального Заказчика часть параметров, необходимых для подготовки первой версии концептуального ТЗ, принимается как проектные допущения. Данные параметры используются для формирования точки отсчета Фазы №1 и подлежат последующей валидации на этапе детального проектирования и архитектурного планирования

| --- | --- | --- |
| SIEM | MaxPatrol SIEM | Проектное допущение |
| EDR | MaxPatrol EDR | Проектное допущение |
| Аутентификация | Корпоративный IdP на базе Keycloak с интеграцией с LDAP/Active Directory | Проектное допущение |

### Уточнения модели аварийной остановки

- Оператор может экстренно остановить активную кампанию;

- администратор платформы имеет право выполнить глобальную аварийную остановку всех активных кампаний;

- после активации kill switch новые действия сценария не запускаются;

- агенты прекращают выполнение активных действий и переходят в безопасное состояние;

- начало остановки должно быть инициировано не позднее 30 секунд с момента подтверждения команды kill switch;

- возобновление симуляций после глобальной аварийной остановки возможно только после завершения проверки инцидента и

разрешения уполномоченного сотрудника ИБ.
